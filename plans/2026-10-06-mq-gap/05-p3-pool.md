## 0. 定位

00 号矩阵把 MQ 能力差距按优先级分为 A 级（Batch 1）、B 级（Batch 2）与 **C 级
（按需 / 悬置）**；01–04 号文档把 A/B 级展开为可执行工作包。本文档是 **C 级的详表**，
与 00 号矩阵互为详表/索引：矩阵给一行结论，本文给触发条件、落点与规模。只做两件事：

1. **按需池**（§2–§3）：15 条"明确有价值、但不进 Batch 1/2"的能力。判据不是优先级
   排序，而是**触发条件**——出现什么真实信号才立项；没有信号就一直是池子里的条目。
2. **显式不做清单（终局）**（§4）：11 条明确**不做**的能力与理由，是对
   `features/mq-lite.md` 路线决策（final）边界的重申，作为后续需求沟通的默认答案。

不在本文范围内：A/B 级条目（归 01–04 号）、验收用例登记（归 06 号总表）。

阅读顺序建议：只关心"现在做什么" → 00 号矩阵 + 01–04 号；被问"什么时候做 X" →
本文 §2；被问"为什么不做 Y" → 本文 §4；维护台账 → §5。

### 0.1 与工作包（01–04）的边界

为防双重登记，已在工作包内的交付物**不得**再入池：

| 工作包 | 已覆盖（不在池内） |
|---|---|
| 01（WP1 引擎可靠性） | DLQ 转移 + maxdelivery、idle>backoff 自动重投、XTRIM MINID、RENAME 提交账本随迁 |
| 02（WP2 延迟消息） | delay 乱序按 due 投递、BLOCK 到期唤醒、kill -9 恢复、HTTP `delay_ms` |

## 1. 性质说明

### 1.1 什么是按需池

- 入池条目同时满足三个条件：
  - **有价值**：真实客户端 / 运维 / 规模诉求可以具体描述（不是"别家有所以我们也要"）；
  - **不紧急**：缺它不阻塞 Batch 1/2 的任何验收点，也不破坏已落地面的正确性；
  - **可独立立项**：不与引擎可靠性（WP1）、延迟消息（WP2）、parity（WP3/WP4）耦合。
- 按需池**不是 backlog**：条目没有排期、没有负责人、没有目标批次。它是一张
  "信号 → 动作"查找表。
- 与显式不做清单的分界：池内条目是"**会做，等信号**"；不做清单是"**不做**，除非
  路线决策本身被推翻"——`features/mq-lite.md` 上半部分路线决策标注 final，不再复议。

### 1.2 触发条件即立项开关

每条池条目都携带**可观测的触发信号**，信号分三类：

| 信号类别 | 形态示例 | 对应条目 |
|---|---|---|
| 客户端侧 | SDK 默认行为变化（新版本只发 v2+ 请求）、AdminClient 启动期强依赖、迁移脚本显式使用某子句 | 1–9 |
| 运维侧 | 长期运行后组查询 / XINFO 输出膨胀、公网暴露后的资源保护诉求 | 8、13、14 |
| 业务侧 | 按时间戳回溯、审计回填、多播消费问询 | 3、12、15 |

信号没出现 = 不立项；任一条命中 = 走 §1.3 立项流程。**不允许**以"顺手实现"为由
绕过触发条件（这正是池与工作包的纪律差异）。

### 1.3 立项流程

触发后不直接写代码，先落计划：

1. 新建 `plans/YYYY-MM-DD-<slug>/` 计划文档，粒度对齐本目录 01–04 号文档：
   目标 / 现状与证据 / 改动面 / e2e / 文档同步；
2. 计划必须回写三件事：
   - 触发信号原文（issue / 日志 / 压测数据 / 客户端版本号）；
   - 从 00 号矩阵 C 级**出池**的标记（矩阵行与本表 §2 行同步删除）；
   - §2 的预估落点与规模是否仍成立（源码拆分会导致路径漂移）；
3. 评审通过后按批次实现与提交（conventional commits），e2e 用例登记进 06 号总表的
   追加区，验收命令沿用其命令块；
4. 合入后在 `features/changelog/` 落 `YYYY-MM-DD/{topic}.md` 条目。

### 1.4 与 00 号矩阵 C 级池的关系

- 00 号矩阵 C 级行 = 本文 §2 表格行的**索引**（一行一条，指回本文条目编号）；
- 本文 = **详表**（触发条件 / 预估落点 / 预估规模 / 分组备注）；
- 两处必须同步变动：出池（立项）时矩阵行删除、本文条目移入新计划；复核淘汰时两处
  一起删（见 §5）；
- 「C-挂起」类（§4.1）**不在池编号内**：它挂在 00 号矩阵的挂起区，重评入口见 §4.1。

### 1.5 三级分诊

新诉求进来时按下表落位，**逐级判断、只落一层**：

| 层 | 判据 | 台账载体 | 动作 |
|---|---|---|---|
| 工作包（A/B 级） | 有验收点、进 Batch 1/2 | 01–04 号文档 + 06 号总表 | 直接实现 |
| 按需池（C 级） | 有价值 + 有可观测触发条件 + 不紧急 | 本文 §2 + 00 号矩阵 C 级 | 等信号 |
| 不做清单（终局） | 无场景，或与路线决策（final）冲突 | 本文 §4 + 00 号矩阵不做区 | 拒绝并指向 §4 行 |
| C-挂起 | 依赖外部能力（数据面复制）落地 | 本文 §4.1 + 00 号矩阵挂起区 | 等复制能力 |

分诊的落位结果写进诉求记录（issue / 沟通留痕），避免同一诉求反复评估。

## 3. 分组备注

### 3.1 Kafka wire 面（条目 1–6）

- 条目 1 与 5 同属 "admin 面"：若触发，**一并立项**（在新 admin 模块内同时落
  CreateTopics/DeleteTopics/CreatePartitions 与 DescribeConfigs 桩），不拆两次，避免
  admin 模块重复起停；
- 条目 4 先于条目 3：by-ts 语义依赖 ListOffsets 版本面扩到 v2+；若同时触发，按
  4 → 3 顺序排；
- 条目 2 是**行为开关**而非能力：实现小，但必须默认关闭，维持面规范"不自动建
  topic/分区"的现状（`features/kafka-front.md` 把该行为定为等价 error 3）；配置键
  仅键名入 `src/conf.rs`，默认值在立项时评审，不得内置凭据类取值；
- 条目 6 是"常量应答"型补齐：不引入真实 epoch 语义，立项计划须写明单节点语义下的
  应答内容与消费者侧预期。

现状锚点（立项时以此复核，漂移即先修文档）：

- 版本面：面规范记载 ListOffsets 注册 v0–v1，未实现版本回 error 35（条目 4）；
- 已知差异：produce 路径落库即丢弃 timestamp，by-ts 按到达时钟回答（条目 3）；
- 映射语义：topic/partition ← parent 流/队列静态映射，队列数即分区数，建/删 topic
  等价于建/删映射两侧对象（条目 1/2）。

### 3.2 Lite 动词面（条目 7–9）

- 三条都是 Redis Streams 动词的**可选子句/子命令**补齐，不动组模型与 PEL 结构；
- 与 01 号（WP1）交付物正交：DLQ / 重投 / MINID 不依赖这三条，反之亦然；
- 若触发时与 01 号改动重叠同一文件（如 `src/lite/claim.rs`），立项计划须显式写
  冲突核对（以 01 号先合入的形态为基线 rebase）；
- 条目 8（XINFO FULL）注意输出规模：条目 14（注册行 idle GC）未做前，大组 FULL
  视图可能很长——两者同时触发时先 14 后 8；
- 条目 7 的语义细节：TIME/RETRYCOUNT/IDLE 是**写侧改写**，不新增读路径；立项时须
  定界"改写后 XPENDING 概要/range 的 idle/deliveries 输出随之变化"的回归；
- 条目 9 的 LIMIT 与 01 号 MINID 的 LIMIT 参数形态同源：若 01 号先合入，实现时
  共享参数解析，不另起一套语法。

### 3.3 HTTP 面（条目 10–12）

- 三条共享同一动机：降低单请求往返成本（网关聚合、批量压测、审计回填）；
- 批量 produce/ack（10/11）只在 `src/rocksmq/api.rs` 编排层循环，**不引入批事务
  边界**：逐条生效、逐条幂等，失败按条返回；
- `/range` 回放（12）复用 Lite 读路径，无新存储语义；立项时须定界"只读、不影响
  消费组水位"；
- 三条都不改鉴权模型：token 门（WP4 落地后）对批量/回放端点同等生效，e2e 复用
  同一 401 矩阵；
- 三条触发常一起出现（同一网关/压测诉求），允许合并为一个计划文档立项。

### 3.4 配置与运维（条目 13–15）

- 条目 13 是资源保护闸门：落点横跨 `src/conf.rs` 与 rocksmq 接入层，注意与既有
  `rocksmq_bind` 键同一配置段、同一 serde 风格；
- 条目 14 的关注点是**输出规模**而非正确性：立项时必须给出"多久无心跳视为死成员"
  的判据、GC 与 XINFO/组查询输出的回归用例，以及与 XGROUP DELCONSUMER 的关系
  （GC 不等价于显式删除，不产生客户端可见错误）；
- 条目 15 是纯文档条目：不写代码，触发即改 `features/mq-lite.md`（living spec 下
  半部分）并记 changelog；文档要写清"每消费者独立组名 = 独立水位 + 独立 PEL"的
  语义代价；
- 条目 13 与既有接入面的资源保护策略对齐（与 `src/conf.rs` 现有配置段同一风格），
  不为单一前端发明新语义。

## 4. 显式不做清单（终局）

以下各项为**终局决策**：不是"暂缓"，而是除非 `features/mq-lite.md` 路线决策
（final）本身被推翻，否则不接受排期。需求沟通时以本表为默认答案；表内没有的诉求
先走 §5.1 入池评估。

| 项 | 理由 | 依据 |
|---|---|---|
| 事务消息 | 无事务引擎；SQL 面事务不覆盖 MQ | `features/mq-lite.md` 路线决策（final）；00 号矩阵 |
| 幂等 producer | 单机 WAL 序即可保证不乱序；跨会话去重交客户端 | 同上 |
| ISR / 多副本 MQ 数据面 | → **挂起待数据面复制**（单列「C-挂起」类，见 §4.1） | 同上 |
| 优先级队列 | 无场景 | 同上 |
| 消息级 TTL | XTRIM MINID 时间窗替代（见 01 号文档） | `features/mq-lite.md` + 01 号文档 |
| 消息轨迹 | 可观测性成本高；metrics + DLQ 覆盖主要排障 | `features/mq-lite.md` 路线决策（final） |
| 增量 fetch session | 全量 fetch 响应在当前规模下足够 | 同上 |
| zstd 压缩 | 仅保留既有压缩位语义；客户端可自行压缩 value | 同上 |
| 消费限流/配额 | fetch 响应 throttle 时间恒 0；限流交客户端侧 | 同上 |
| TLS | 部署面由 LB / 代理承担 | 同上 |
| 全量 Redpanda 兼容 | 以 Kafka 官方客户端兼容为准 | 同上 |

使用口径：

- **不做 ≠ 不修 bug**：已落地面上与规范不一致的行为仍按缺陷修（走缺陷流程，不经
  本表复议）；
- **不做 ≠ 不记录**：用户提出本表内的诉求时，在 issue/沟通记录中指向本表行，不改
  表、不排队；
- 压缩条目的中性表述：仅保留既有压缩位语义——不新增 zstd 译码，也不承诺逐 codec
  全集；客户端需要更高压缩率时自行压缩 value。

### 4.1 C-挂起：ISR / 多副本 MQ 数据面

- 单列一类而非并入不做：`features/mq-lite.md` 的结论是"先数据面复制、再谈协议"——
  单节点持久性风险被**显式接受**，但若数据面复制能力落地，本项须**重评**；
- 重评 ≠ 自动立项：仍走 §1.3 流程（新建计划、给出范围与验收），只是免掉"等触发
  信号"这一步；
- 台账形态：00 号矩阵标「C-挂起」，不占按需池编号，不出现在 §2；
- 重评入口：复制能力落地批次合入后的第一次季度复核（§5.3）主动开启，不等用户
  报障。

### 4.2 不做清单与缺陷修复的分界

- 分界判据：**行为是否已被文档承诺**。已承诺而未兑现 = 缺陷，走缺陷流程修复；
  未承诺 = 新能力诉求，进 §1.5 分诊；
- 例：headers 的 envelope 内嵌形态是 `features/kafka-front.md` 文档化的既有承诺，
  03 号把它收敛为"真 headers 回放 + 存量 envelope 兼容"——属语义收敛，不经本表
  复议；
- 若某条"不做"项被发现存在既有承诺证据，提级为缺陷处理，并在
  `features/changelog/` 记录提级理由；本表行随之删除并在 00 号矩阵同步。

## 5. 池治理

### 5.1 入池规则

- 新候选必须能写出**至少一条可观测触发条件**；写不出来的，归入 §4 不做清单评估
  或直接拒绝，**不得**以"待定触发条件"名义挂池；
- 入池动作 = 00 号矩阵加 C 级行 + 本文 §2 加行，两处同一 PR；
- 池不设条目上限，但季度复核时清理"描述不出场景"的陈旧条目（见 5.3）。

### 5.2 出池（立项）规则

- 任一触发条件命中即出池，走 §1.3 立项流程；
- 出池条目从 00 号矩阵 C 级与本文 §2 **同步移除**，不留"进行中"悬态——状态归新
  计划文档管；
- 出池条目的 e2e 用例登记进 06 号总表追加区，验收命令沿用其命令块；新 e2e 文件
  同样受"每份 <400 行"硬上限约束；
- 同一信号触发多条相邻条目时允许合并立项（如 §3.1 的 admin 面两件套），合并范围
  写进计划文档。

### 5.3 复核节奏

- **季度复核或触发即评**：每季度对全池过一遍；任一条目触发时立即单评；
- 复核内容：触发条件是否仍成立（SDK 版本演进可能让条目永久失去意义）、预估落点
  是否漂移（源码拆分后路径变化）、预估规模是否失真；
- 复核产出：淘汰条目直接删（两处同步），保留条目更新备注；结论在
  `features/changelog/` 记一条 `YYYY-MM-DD/{topic}.md`；
- 复核同时检查「C-挂起」类是否有重评条件成熟（§4.1）。

季度复核清单（逐项打勾后归档进复核记录）：

```
[ ] 全池逐条：触发条件仍成立？（SDK/客户端版本事实有无变化）
[ ] 落点复核：预估落点路径仍存在？（注意 800 行上限触发的拆分）
[ ] 规模复核：小/中分级是否漂移？
[ ] 「C-挂起」：数据面复制能力是否已落地？落地则开启 §4.1 重评
[ ] 台账一致性：00 号矩阵 C 级行数 == 本文 §2 行数？
[ ] 淘汰/更新结论：changelog 条目已落？
```

### 5.4 台账同步

- 池的任何变动（入池 / 出池 / 淘汰 / 复核结论）一律三件套同批完成：改 00 号矩阵、
  改本文、`features/changelog/` 记录；
- 禁止只改一处：矩阵与详表失同步即视为台账破损，下一次复核的第一件事就是修复；
- 本文档自身的修订（触发条件措辞收紧、落点更新）不要求 changelog，除非改变了
  条目的立项语义。

### 5.5 反模式（治理红线）

- **池变 backlog**：给条目加排期/负责人/目标批次——出现即视为分诊失败，退回
  §1.5 重评；
- **无信号抢跑**：以"顺手""低风险"为由提前实现池内条目——实现可以，但必须先走
  §1.3 立项（哪怕当天完成），保证台账与 changelog 完整；
- **触发条件稀释**：把触发条件改写成"有人提到"级别的弱信号——弱信号只登记不
  立项，立项标准不变；
- **不做清单复议循环**：同一诉求被拒后换个措辞再提——分诊记录（§1.5）里留痕，
  重复诉求直接指向 §4 对应行。

## 附录 A：触发信号登记模板

池条目被触发时，在诉求记录（issue / 工单）中按下表登记，作为 §1.3 第 2 步的输入：

```
触发条目：#<本文 §2 编号>（多条则逐条列）
信号原文：<issue 链接 / 日志摘录 / SDK 版本号与复现步骤>
影响面：<受阻的客户端 / 业务 / 运维流程>
诉求方期望：<期望的行为或接口>
分诊结论：<立项（进 §1.3） / 观望（说明观望理由与再评条件） / 指向 §4 不做行>
登记人 / 日期：<...> / <YYYY-MM-DD>
```

登记原则：

- 信号原文必须**可追溯**（能回放到日志或复现步骤），不接受转述；
- "观望"结论要写明再评条件（如"等 SDK 升级占比过半再评"），不得无限期观望；
- 登记本身不改台账：只有立项/淘汰才触发 §5.4 的三件套。
